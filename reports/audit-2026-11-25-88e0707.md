# Independent Implementation Audit — Arcline at `88e0707`

**Audited commit:** `88e0707` ("JSON-RPC session (arcline-cli rpc) and foundation handover"), branch `main`.
**Date:** 2026-11-25. **Scope:** whole repository: architecture docs, ADRs, all Rust and C sources, build
scripts, dependencies, licensing, tests. A companion document specifies the FFmpeg upgrade:
[docs/specs/ffmpeg-9.1-upgrade.md](../docs/specs/ffmpeg-9.1-upgrade.md).

**Rules of this audit:** no implementation code was changed. All experiments ran outside the repository
(temporary directories, scratch crates that depend on the repo crates by path, and a small C probe linked
against the pinned FFmpeg 8.1.3 libraries). Every finding marked **verified** was reproduced. Findings
marked **analysis** come from reading the code and were not reproduced.

---

## 0. Executive summary

The approved architecture is sound, and the code follows it closely: six crates with the documented
dependency directions, one writer thread, acknowledgement only after the journal write, FFmpeg structs kept
inside a C shim, and exports in a separate process. The foundation (Phases A, P, B) is real: the workspace
builds, all 65 tests pass, and the core command and journal code is unusually well tested.

The test suite proves the **happy path on lossless, intra-only, synthetic media**. Outside it, the audit
found defects the suite cannot see:

| # | Finding | Severity | Status |
|---|---|---|---|
| F-01 | Acknowledged edits are lost after a journal entry is rejected on replay | **Critical** | verified |
| F-02 | Heap buffer overflow in the shim on a mid-stream resolution change (export crashes, `0xC0000005`) | **Critical** | verified |
| F-03 | Invalid memory access in the shim on a mid-stream audio channel change (`0xC0000005`) | **Critical** | verified |
| F-04 | Creating a project overwrites an existing container *before* taking the lock, destroying saved work of an open session | **Critical** | verified |
| F-05 | A stale autosave sidecar resurrects a different project; new edits are lost | High | verified |
| F-06 | Exported audio is corrupted every 4,096 samples for AAC, MP3, Opus and resampled sources | High | verified |
| F-07 | Opus audio from MKV/WebM is placed 48 samples (1 ms) late | High | verified |
| F-08 | Random access returns the wrong frame for MPEG-TS and for MP4 with B-frames (silently) | High | verified |
| F-09 | Network and other protocols are reachable from document asset paths; clients can bypass the import check | High | verified |

Both media crashes (F-02, F-03) happen on files that the subprocess import check classifies as `ok`. The
isolation design assumed that the `ffmpeg` CLI and the in-process shim fail on the same inputs. They do not:
the CLI reconfigures its filters when stream parameters change; the shim does not.

**FFmpeg 9.1:** the shim compiles against the 9.1 headers with zero warnings
(`-Wall -Wextra -Wdeprecated-declarations`), and none of the libav functions, fields or constants it uses
were removed or deprecated. The upgrade risk sits in the build, packaging, licensing and verification work, not in the
API. Because 9.1 adds a Windows `handle:` protocol and a libcurl protocol, the upgrade must also close
F-09, or it widens the attack surface. The spec orders the work so that the critical shim defects are
fixed on 8.1.3 first; the version bump can then be checked by a differential test.

**Status correction:** Phase B is functionally complete, but four of its documented exit criteria are not
met (§5.1). HANDOVER.md has been updated accordingly.

### 2.2 Architectural defects (implementation-level; no redesign required)

- **AR-1: the import check is necessary but not sufficient.** The child-process check runs `ffprobe` and
  three one-second `ffmpeg` decodes. The `ffmpeg` CLI reinitialises its filter graph when frame size or
  channel layout changes; the shim builds its converters once. Inputs that are harmless to the CLI
  therefore crash the shim (F-02, F-03). The shim must be robust to parameter changes by construction; the
  check cannot be the guard. This keeps ADR-0003's design and closes the gap it assumed was closed.
- **AR-2: the document is untrusted input, and the session layer is bypassable.** Asset paths come from
  project files (possibly from other people) and from agent commands. `project.apply` passes a
  client-supplied `asset.import` (any path or URL, `status: "ok"`) straight to the engine, so the import check and
  quarantine can be skipped, and the shim then opens whatever string it is given with all compiled-in
  protocols (F-09). docs/06 §4.1 already requires the session layer to resolve file-referencing commands;
  the RPC session does not do so yet.
- **AR-3: recovery trusts the sidecar too much.** Snapshot selection does not check project identity
  (F-05); a semantically rejected journal record is left in place and new records are appended after it
  (F-01); project creation does not lock before writing (F-04).
- **AR-4: the audio read model and the decoder disagree.** `SampleSource` is random access by sample index,
  and the mixer reads each block plus one sample of lookahead. The shim's audio reader is forward-only and
  discards consumed samples, so every block after the first re-seeks the decoder, which loses pre-roll and
  resets the resampler (F-06).
- **AR-5: frame accuracy depends on demuxer seek semantics.** The shim assumes
  `av_seek_frame(target_pts, BACKWARD)` lands on a keyframe whose PTS ≤ target. MOV indexes by DTS, and
  MPEG-TS has no index, so the assumption fails. The fallback returns a later frame without any error (F-08).
- **AR-6: there is no runtime identity check of the loaded FFmpeg.** Headers are checked at build time only;
  the DLLs found at run time and the `ffmpeg`/`ffprobe` found on `PATH` are trusted blindly (F-21). This
  is the main hazard for the 9.1 upgrade.
- **AR-7: the parity contract needs deterministic sources.** FFmpeg's AAC decoder output depends on decode
  history (F-25). The preview/export parity test of docs/05 §7 must use PCM or FLAC fixtures, or the same
  decode history on both sides.

## 3. Findings

Severity: **Critical**: loss of acknowledged edits, or memory corruption triggerable by media.
**High**: silent wrong output in a core promise, or a security boundary gap. **Medium**: functional
defect or documented promise not met. **Low**: robustness or quality issue. **Info**: observation.

### F-01 — Acknowledged edits lost after a rejected replay · Critical · verified

- **Where:** `crates/arc-core/src/runtime.rs:145-163`, `crates/arc-core/src/store.rs:443-446`.
- **Evidence (experiment F):** session 1 saves revision 1, then makes an unsaved edit that adds effect
  `core.x` (revision 2, acknowledged). Session 2 opens with a catalog without `core.x`: replay rejects the
  first record (`replayed: 0, discarded_records: true`). Session 2 then acknowledges revisions 2 and 3.
  Session 3 opens at **revision 1**: both acknowledged session-2 edits are gone.
- **Root cause:** when the *first* journal record is rejected, `EngineHost::open` calls
  `write_snapshot(snapshot, base_revision)`. Because the revision did not change and the journal file
  exists, `write_snapshot` keeps the old journal (`if old != rev || !jpath.exists()`). The rejected record
  passed CRC and decoding, so `ProjectStore::open` positioned the writer *after* it. New records are
  appended behind the rejected one, with a duplicate revision number; the next replay stops at the rejected
  record again and discards everything after it.
- **Triggers:** any record that decodes but fails validation: an effect removed or a parameter range
  narrowed between app versions, validation tightened, or a catalog mismatch between processes.
- **Fix (within the design):** after a rejection, always start a new journal at the recovered revision
  (truncate or rotate even when the revision is unchanged), keeping the rejected bytes in
  `journal-<rev>.bin.rejected` as docs/08 §4.6 already requires. **Test:** the experiment F scenario as an
  `arc-core` integration test.

### F-02 — Heap buffer overflow on a mid-stream resolution change · Critical · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:171-188` (`to_rgba`), `crates/arc-media/src/libav.rs:203,235-237`.
- **Evidence (experiment J):** MPEG-2 stream, 320×180 for 2 s then 640×360, concatenated into one MKV.
  `ffprobe` reports 320×180. The import check says **`ok`**. `arcline-cli render` dies with **`0xC0000005`**
  (access violation).
- **Root cause:** the Rust side allocates `width × height × 4` bytes from the *stream* parameters and passes
  that stride. `to_rgba` builds the swscale context from the *frame* size (`sws_getContext(f->width,
  f->height, …, f->width, f->height, RGBA)`) and writes `f->width × 4` bytes per row for `f->height` rows.
  A larger frame writes about 230 KB past the buffer in this test. The `SAFETY` comment in `libav.rs`
  ("it scales to the stream's native size") is false.
- **Impact:** memory corruption in our own code, triggered by ordinary media (resolution switches occur in
  screen recordings, concatenated files and adaptive streams). The import check does not detect it.
- **Fix:** the shim must always scale to the destination size it was given (pass `dst_w`, `dst_h` from
  Rust and use them in `sws_getContext`), and reject or rescale frames whose size differs. **Test:**
  experiment J as a fixture-based test (no crash; frames scaled or a typed error).

### F-03 — Invalid memory access on a mid-stream audio parameter change · Critical · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:259-275` (`ensure_swr`), `:347-358`.
- **Evidence (experiment K):** MP2 elementary stream, stereo for 2 s then mono. Import check **`ok`**.
  Render dies with **`0xC0000005`**. Control with stereo + stereo renders 80 frames normally.
- **Root cause:** the resampler is configured from the first decoded frame and is recreated only when the
  *output* rate changes. A later frame with a different channel count, sample format or sample rate is fed
  to `swr_convert` with the old input layout: for planar stereo, swresample reads `extended_data[1]`,
  which is `NULL` for a mono frame.
- **Fix:** compare `format`, `sample_rate` and `ch_layout` of every frame with the configured input and
  rebuild the resampler on change (`swr_config_frame` or a fresh `swr_alloc_set_opts2`). **Test:** the
  experiment K fixture.

### F-04 — Project creation overwrites before locking · Critical · verified

- **Where:** `crates/arc-core/src/store.rs:340-358` (`ProjectStore::create`); CLI `new`
  (`crates/arc-cli/src/main.rs:210-224`); RPC `project.open` with `create` (`crates/arc-cli/src/rpc.rs:259-271`).
- **Evidence (experiment H):** session A creates `h.arcline`, adds a track, saves revision 1 and stays open.
  `arcline-cli new h.arcline --name "PROJECT B"` fails with "project is open in another process", **but the
  container already holds PROJECT B**. When session A closes cleanly it deletes its sidecar (its last
  revision was saved), and the project now opens as an empty PROJECT B: A's saved work is gone.
- **Root cause:** `create` calls `save_container` before `SessionLock::acquire`, and never checks whether
  the path already exists. Secondary: the CLI reports the lock failure as kind `io_error` instead of
  `project_locked`.
- **Fix:** acquire the lock first; refuse to create over an existing container unless an explicit
  overwrite flag is given; map the error to `project_locked`.

### F-05 — Stale sidecar resurrects a different project · High · verified

- **Where:** `crates/arc-core/src/store.rs:311-336` (`latest_snapshot`), `:340-358`, `:369-376`.
- **Evidence (experiment C2):** an unsaved session of PROJECT A leaves `snapshot-1.json`. The user deletes
  the container; an agent creates PROJECT B at the same path through RPC, edits it, and ends the session
  without saving. Reopening shows **PROJECT A** (`recovered: base sidecar`); B's edit is lost. (With CLI
  `new`, experiment C, the immediate save and clean close remove the stale files, so the bug needs a
  create-without-save path such as RPC or the future GUI.)
- **Root cause:** `create` does not clear an existing sidecar, and `latest_snapshot` picks the highest
  revision without checking that its `meta.id` matches the container's project id.
- **Fix:** on create, move any existing sidecar aside (for example `<name>.arcline.autosave.stale-<time>`);
  in `open`, ignore snapshots whose project id differs from the container's.

### F-06 — Exported audio corrupted every 4,096 samples · High · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:294-311` (reposition test `start < buf_start`), `:348-354`;
  `crates/arc-audio/src/lib.rs:136-140` (each block reads `last − first + 2` frames);
  `crates/arc-cli/src/export.rs:142` (block size 4096).
- **Evidence (experiment D):** for the same source, exported PCM vs `ffmpeg` reference decode:

  | Source | Frames differing (of 189,952) | Max abs error | Pattern |
  |---|---|---|---|
  | FLAC 48 kHz | 0 | 0 | exact |
  | AAC 48 kHz (sine) | 42,621 | 0.108 | clusters every **4,096** samples |
  | MP3 48 kHz (sine) | 62,280 | 0.103 | clusters every 4,096 samples |
  | Opus in MKV (sine) | 188,737 | 0.157 | entire stream (see F-07) |
  | FLAC 44.1 kHz → 48 kHz | 60,748 | 0.0025 | 4,096-sample clusters at block re-seeks |

  The sine has amplitude 0.125, so a 0.108 error is a full-scale click, about 11.7 per second.
- **Root-cause confirmation (experiment D′):** driving `AudioDecoder` with one long read gives exact output
  for MP3, Ogg Opus and 44.1 kHz FLAC; driving it with the mixer's pattern (4,096 frames, each read one
  frame longer) reproduces the corruption. Three mechanisms combine:
  1. **Re-seek per block.** Each read consumes one more frame than the block advances, so the next read
     starts *before* the buffered position; the shim treats that as a backward seek.
  2. **No pre-roll after a seek.** After `avcodec_flush_buffers`, MDCT codecs (AAC, MP3, Opus) need warm-up
     frames that are never decoded and discarded.
  3. **Resampler reset.** The shim frees the resampler on every reposition, so resampled sources
     restart the filter state at each block.
  Also, the very first read always seeks (the `swr == NULL` branch), so even position 0 is decoded as a
  post-seek stream: the first 574 samples of the AAC file match `ffmpeg -ss 0` exactly, not a plain decode.
- **Impact:** phone and camera MP4s carry AAC; every export of such footage has audible clicks. The test
  suite misses it because the end-to-end test uses FLAC in MKV and checks only RMS. HANDOVER's "block-size
  parity" claim holds for the synthetic `Ramp` source only.
- **Fix (within the design):** keep a small history window (≥ 1 block) in the shim so overlapping reads are
  served from the buffer; on a real seek, seek earlier by `max(codecpar.seek_preroll, decoder pre-roll,
  one codec frame)` and discard up to the target; keep the resampler and flush it with `swr_init` only on
  discontinuities; do not seek on the first read at position 0. **Tests:** experiment D′ (block pattern
  equals one long read, exactly) for FLAC, MP3, Ogg Opus, 44.1 kHz; tolerance-based for AAC (see F-25).

### F-07 — Opus from MKV/WebM placed 1 ms late · High · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:348-354`.
- **Evidence (experiment D′, white noise, unambiguous lag):** a single long read of Opus in MKV is the
  reference shifted by **48 samples**; the same audio in Ogg is exact (lag 0). `ffprobe` shows the MKV
  stream in a 1/1000 time base with the first packet at −7 ms and `initial_padding=312`; Ogg uses 1/48000.
- **Root cause:** the shim derives the sample index of buffered audio from the first decoded frame's
  timestamp. MKV timestamps have 1 ms resolution, so the anchor is off by up to one millisecond, and it is
  re-derived after every seek (F-06), adding jitter.
- **Fix:** anchor sample positions with sample precision: after a seek, decode from an earlier point and
  count samples from a timestamp known exactly (stream start or a packet with an exact sample position),
  or round the anchor to the codec frame grid. **Test:** white-noise Opus in MKV and Ogg, exact alignment.

### F-08 — Random access returns a later frame · High · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:210-250` (seek, then "target precedes the first frame"
  fallback at 246-250).
- **Evidence (experiment G):** 90-frame counter video at 30 fps, GOP 15 (MPEG-4) or 30 (H.264), 2 B-frames.

  | Source | Sequential render | Random access (fresh process per frame) |
  |---|---|---|
  | MPEG-2, MKV (open GOP) | exact | exact |
  | MPEG-2, MPEG-TS, start 1.433 s | **all 88 frames wrong**: each shows the next I-frame (0–12 → 15, 13–27 → 30, …) | requested 0/13/28/44/59 → got 15/30/45/60/75 |
  | MPEG-4 Part 2, MP4 | exact | requested 13, 14, 28, 29, 44, 59 → got 15, 15, 30, 30, 45, 60 |
  | H.264 (QSV), MP4 | exact | exact at all 18 sampled positions |

- **Root cause (experiment G′, C probe):**
  - *MP4:* the MOV index is keyed by DTS. For target frame 13.5 the seek lands on the keyframe with
    **DTS 12 but PTS 15**, the first decoded frame is 15, and the shim's fallback returns it as if it were
    the target. The frames just before each keyframe are unreachable by random access.
  - *MPEG-TS:* there is no index (`0 entries`); the timestamp search lands on a non-key packet
    (`key 0`), and the decoder's first output is the next I-frame (15, then 30), past the target.
  - *MKV:* cue-based seek by PTS lands correctly.
- **Impact:** wrong frames, silently, for clips that start mid-GOP and for any seek. Affects preview
  scrubbing (Phase C) and exports. MPEG-TS covers AVCHD/`.MTS` camcorder files.
- **Fix:** after a seek, if the first decoded frame's PTS is greater than the target, seek again to an
  earlier point (back off by one GOP or a growing interval) until a frame ≤ target is decoded; seek with a
  margin of `has_b_frames`/reorder depth; return a typed error instead of a later frame when no earlier frame
  exists; consider `AVSEEK_FLAG_ANY` plus decode-forward for un-indexed formats. **Tests:** experiment G as
  fixtures (TS with a non-zero start, MP4 with B-frames, open GOP), random access to every frame.

### F-09 — Non-file protocols reachable; import check bypassable · High · verified

- **Where:** `crates/arc-media/csrc/arc_av.c:86` (`avformat_open_input(path, NULL, NULL)`);
  `crates/arc-cli/src/rpc.rs:115-138`; `crates/arc-core/src/command.rs:552-580`.
- **Evidence (experiment I):** `apply` accepts `asset.import` with path `http://127.0.0.1:9/x.mp4` and
  `status: "ok"`; the render warning is `open: Error number -138 occurred`, a network error from the HTTP
  protocol, not "file not found". The CLI `probe`/`import` path is protected only by `path.exists()`.
- **Exposure:** the pinned 8.1.3 build compiles in about 40 input protocols (http(s), ftp, rtmp, sftp, srt,
  rist, zmq, tcp, udp, …). 9.1 adds `libcurl` and a Windows `handle:` protocol (`libavformat/file.c:613`),
  which reads from a Windows handle number. A project file or an agent can therefore make the in-process
  decoder contact the network, read inherited handles, or open local files through `concat:`/`subfile,`
  prefixes. In addition, the client-supplied `status: ok` skips quarantine.
- **Fix:** open only `file:` URLs built from canonical absolute paths, with
  `protocol_whitelist=file` in the open options; reject any asset path with a URL scheme at the session
  layer; run the import check in the session layer for every client `asset.import` (as docs/06 §4.1 says)
  and ignore client-supplied `status`/`probe`; build the shipped FFmpeg with `--disable-network` and only
  the `file` and `pipe` protocols. These are part of the 9.1 spec.

### F-10 — No path allow-lists; render output overwrites anything · Medium · analysis

`job.submit` and `render` accept any output path, and the encoder runs `ffmpeg -y`
(`crates/arc-media/src/encode.rs:196`), which overwrites existing files. The temporary
`.<name>.audio.wav` is written next to the output. docs/01 §6.3 and docs/06 §8 promise `--root` and
`--output-root`; neither exists.

### F-11 — Phase B status overstated · Medium · verified (document check)

See §5.1. HANDOVER marked Phase B "Done"; four exit criteria or deliverables are open.

### F-12 — Phantom redo after recovery · Medium · verified

- **Where:** `crates/arc-core/src/engine.rs:441-457`.
- **Evidence (experiment E):** edit (rev 1), undo (rev 2), redo (rev 3); a second redo correctly fails with
  `nothing_to_redo`. After reopening (3 records replayed) `history.redo` **succeeds** (rev 4).
- **Root cause:** replaying an `Undo` record moves the history entry to the redo stack, but replaying a
  `Redo` record pushes a new undo entry *without popping the redo stack*. Redo then re-applies a batch that
  is already applied: harmless for a rename, a `duplicate_id` error for clip creation, a second application
  for relative edits.
- **Fix:** for `EntryKind::Redo`, pop the redo stack (as `Engine::redo` does) instead of building a new entry.
  **Test:** extend `replay_reproduces_revisions` with undo + redo and compare `can_redo()`.

### F-13 — Split and in-trim of clips with speed ≠ 1 rejected at half the positions · Medium · verified

- **Where:** `crates/arc-core/src/command.rs:874` and `:819` derive `source_in = offset × speed`;
  `validate_clip` (`:1387-1400`) requires `source_in` on a *sequence* frame boundary.
- **Evidence (experiment B):** a half-speed clip at 30 fps splits at frame 30 but fails at frame 31 with
  `off_frame_boundary: source_in 31/60s`; an in-edge trim by one frame fails the same way.
- **Note:** docs/02 §2.3 requires `source_in` *given as timecode* to be frame-aligned; derived values are not
  addressed. A decision is needed (allow rational `source_in` when `speed ≠ 1`, or quantise derived values);
  either keeps the time model.

### F-14 — Snapshot/journal rotation is not atomic · Medium · analysis

`write_snapshot` (`crates/arc-core/src/store.rs:432-453`) writes `snapshot-R.json` and then opens
`journal-R.bin`. If the second step fails, the snapshot exists but appends continue in the old journal;
recovery picks snapshot R and an empty journal R, losing later acknowledged records. The journal thread
ignores the error (`crates/arc-core/src/runtime.rs:531-535`). Fix: open the new journal before publishing
the snapshot (write snapshot as `.tmp`, open the journal, then rename), or treat failure as degraded mode.

### F-15 — No panic containment in the engine thread · Medium · analysis

docs/01 §9 promises that the engine catches panics per batch and degrades; ADR-0003 promises
`catch_unwind` at decoder calls. Neither exists (`catch_unwind` appears nowhere). A panic in
`apply_command` ends the engine thread; every later request gets "session has ended".

### F-16 — Rotation and pixel aspect ratio ignored · Medium · analysis

`VideoInfo.rotation` is probed and stored but never used by planning or rendering; there is no
sample-aspect-ratio field. Portrait phone footage renders sideways and anamorphic footage is distorted.
docs/04 §2 says rotation "is normalized into the asset at import and applied in the compositor; phone
footage just works."

### F-17 — Whole export audio held in memory; WAV size field overflows · Medium · analysis

`Mixer::render` returns one `Vec<f32>` for the whole range (`crates/arc-cli/src/export.rs:142`): about
1.4 GB for one hour of 48 kHz stereo. `write_wav_f32` stores the data length as `u32`
(`crates/arc-audio/src/lib.rs:193`), so ranges above about 3.1 hours produce a corrupt header. Fix: stream
blocks to the WAV (or pipe), and use RF64/W64 above 4 GB.

### F-18 — Sources larger than the default GPU texture limit abort the export · Medium · analysis

The renderer requests default device limits (`crates/arc-render/src/renderer.rs:200-203`); `wgpu`'s default
maximum 2D texture size is 8,192. A larger still (for example a 100 MP photo) fails texture validation,
which panics under wgpu's default error handler. Fix: request the adapter's limits and downscale oversized
sources in the shim.

### F-19 — Software H.264 encoders contradict the codec posture · Medium · verified (code vs docs)

`VideoCodec::H264` candidates include `h264_mf` and `libopenh264` (`crates/arc-media/src/encode.rs:42-48`);
docs/04 §5 says "none shipped except hardware" and docs/11 §2.2 says OpenH264 is not shipped. An
OpenH264 build compiled from source (as in the pinned BtbN build) does not carry Cisco's patent licence,
which covers Cisco's binaries only. The owner must decide; the spec keeps the code unchanged and excludes
`libopenh264` from the shipped build by default.

### F-20 — The pinned FFmpeg build does not match the documented licence posture · Medium · verified

The installed build (`ffmpeg-n8.1.3-41-ga8029b6528-win64-lgpl-shared-8.1`) is configured with
`--enable-version3` (its `LICENSE.txt` is LGPL **v3**; `ffmpeg -L` says "version 3 or later"), links about 60
external libraries statically into the DLLs (including gmp and libaribb24 (LGPL-3.0) and opencore-amr
(Apache-2.0), the reason for version 3), and enables network protocols. docs/04 §9 and docs/11 §2.1 describe
"LGPLv2.1-compatible components only". Not a licence violation by itself, but the distribution obligations,
the third-party notice set and the attack surface differ from the documented posture. The spec defines a
minimal LGPL-2.1 build and a decision gate.

### F-21 — No version or licence check of FFmpeg at build or run time · Medium · analysis

`build.rs` accepts any FFmpeg (`pkg-config` fallback `atleast_version("0")`, line 28), triggers rebuilds
only on `csrc/arc_av.c` and the `ARCLINE_FFMPEG_DIR` variable (swapping files in the same directory does
not rebuild the shim), and nothing checks `avcodec_version()` or `avcodec_license()` at run time.
`tools::tool()` falls back to `ffmpeg`/`ffprobe` on `PATH` (`crates/arc-media/src/tools.rs:22`); on this
machine a GPL "essentials" build is on `PATH`. Central to the upgrade; specified in the spec.

### F-22 — VFR detection disables the half-frame bias · Low · analysis (unverified risk)

`vfr = avg_frame_rate ≠ r_frame_rate` (`crates/arc-media/csrc/arc_av.c:122`) also fires on constant-rate
files whose average is computed from a rounded duration. For such files `frame_at` drops the half-frame bias
(`crates/arc-media/src/libav.rs:219-227`), and the millisecond-rounding miss that bug 3 of HANDOVER §4
fixed can come back in MKV. Add a fixture with `avg ≠ r` in MKV.

### F-23 — Colour conversion parameters fixed at converter creation · Low · analysis

`to_rgba` (`arc_av.c:172-184`) rebuilds the swscale context only on size or format change; a mid-stream
change of `colorspace` or `color_range` keeps the old matrix. HDR transfer functions are not tone-mapped
(post-1.0 per docs/03).

### F-24 — Lock and error-kind mapping · Low · verified (H) / analysis

`new` reports a locked project as `io_error` (`crates/arc-cli/src/main.rs:218-219`).
`SessionLock::acquire` maps every `PermissionDenied` to `Locked` (`crates/arc-core/src/store.rs:251-255`),
so a read-only folder is reported as "open in another process".

### F-25 — AAC decode output depends on decode history · Info (affects test design) · verified

On noise-like content, FFmpeg's own decode of the same AAC file differs in 184,851 of 192,000 frames with
and without `-ss 0`. This is consistent with the perceptual-noise-substitution generator being reset only
at decoder init (`random_state` assigned at `aacdec.c:1265` in 8.1.3 and `:1380` in 9.1; `flush()` clears
only the overlap buffers). Consequence: the docs/05 §7 hash-parity test must not use AAC sources, and AAC
export audio cannot be bit-exact against an independent decode.

### F-26 — Declared MSRV is wrong · Low · verified

`rust-version = "1.85"` (`Cargo.toml:15`), but `egui` 0.37 declares 1.95, `zip` 9.8 declares 1.89 and `wgpu`
30 declares 1.87. The effective minimum is at least 1.95; the tested toolchain is 1.100.

### F-27 — Job and temporary-file hygiene · Low · analysis

The render job's temporary snapshot (`%TEMP%/arcline-<pid>-j_N.json`, the full document) is deleted only
when `job.status` observes completion (`crates/arc-cli/src/rpc.rs:388`); jobs that are cancelled or finish
without a later `job.status` call leak it, and the session's shutdown does not clean up. The temporary WAV is left behind when the encoder fails (`export.rs:233-234` runs only on success).
The jobs map is never pruned. `job.status` has no `progress` or `queued` state (docs/06 §4.1).

### F-28 — `avcodec_send_packet` `EAGAIN` drops the packet · Low · analysis

`next_frame` (`arc_av.c:155-162`) unreferences the packet when sending returns `EAGAIN`. With the current
receive-first loop this should not happen, but the packet must be kept and resent, not dropped.

### F-29 — Removing a locked track is allowed · Low · analysis

`TrackRemove` (`crates/arc-core/src/command.rs:509-514`) does not check `locked`, while every clip command
does.

### F-30 — Idempotency keys are not bound to the request · Low · analysis

A repeated key returns the cached result even when the commands differ, and it is checked before
`base_revision` and control (`crates/arc-core/src/engine.rs:194-208`). Bind the key to a hash of the
commands and the client.

### F-31 — PoC-only embed messages accepted by the product binary · Low · analysis

`poc.hang` blocks the UI thread on request (`crates/arc-app/src/embed.rs:34-36`, `app.rs:228`). Gate PoC
messages behind `--poc-seconds` or a cargo feature before the embed channel moves to the named pipe.

### F-32 — Probe duration for variable-bitrate elementary streams · Info · verified (K)

For the MP2 stream with a bitrate change, the probe reported 3.024 s for 4.0 s of audio, because the
duration falls back to the container's bitrate estimate (`crates/arc-media/src/probe.rs:137-141`). Clips
near the real end are then rejected with `source_range_exceeded`. Consider a full-scan duration in the
background probe (docs/04 §2 already plans one).

### F-33 — Known performance debt · Info

Per-frame `to_vec` copies of every decoded frame (`export.rs:182`; HANDOVER §6.8), a new uniform buffer and
bind group per render pass, a new readback buffer per frame, CPU YUV→RGB, a synchronous GPU wait per frame.
Budgets (docs/08 §2) remain unmeasured.

## 6. Dependencies and licensing

- **Rust dependencies:** 395 packages in `Cargo.lock`. Direct dependencies are mainstream and permissively
  licensed (MIT/Apache-2.0, `blake3` CC0/Apache, `im` MPL-2.0+). `im` 15.1.0 has had no release since 2022;
  consider the maintained fork `imbl` when convenient (same API family). No `cargo-deny`/`cargo-audit` run
  exists; advisories were not checked offline in this audit.
- **FFmpeg:** see F-19, F-20, F-21 and the spec §6. The current development build is acceptable for
  development; it is **not** a shippable configuration under the documented posture.
- **Toolchain runtime:** MinGW binaries depend on `libwinpthread` and the GCC runtime; the shipped package
  must include their licence notices (GCC Runtime Library Exception; winpthreads licence) if those DLLs are
  shipped.
- **Patents:** posture unchanged (hardware H.264/HEVC encode, SVT-AV1 software); F-19 needs a decision.

## 7. Tests: what is proven and what is not

**Proven well:** exact time and timecode (exhaustive 24 h DF round trip), command semantics and
atomicity, the undo invariant over 10,000 random sequences, journal torn-tail handling at every byte offset,
fault injection, forced-kill recovery, GPU determinism and colour maths, mixer block-size independence with a
synthetic source, frame-exact export through FFV1 and H.264 (sequential).

**Not covered (each maps to a finding):**

| Gap | Finding |
|---|---|
| Replay rejection followed by new edits | F-01 |
| Redo in replayed history | F-12 |
| Creation over an existing or locked project; stale sidecar | F-04, F-05 |
| Long-GOP, B-frame, MPEG-TS, open-GOP random access | F-08 |
| Lossy and resampled audio through the real decoder in mixer block pattern | F-06, F-07 |
| Mid-stream parameter changes | F-02, F-03 |
| Non-file paths and client-supplied `asset.import` | F-09 |
| Speed ≠ 1 split/trim | F-13 |
| Mutated-media corpus through the import check (Phase B exit) | F-11 |
| Rotation, SAR, large stills, VFR-flagged MKV | F-16, F-18, F-22 |

All tests use generated media, as required by docs/08 §6; every experiment in this audit used
generated media too, so each can become a regression test without third-party files.
