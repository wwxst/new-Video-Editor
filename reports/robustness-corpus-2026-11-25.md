# Robustness corpus and decode error contract (2026-11-25)

**Goal (Phase B, goal B):** malformed media must converge to a structured error at the decode
boundary and be marked unavailable, never crash the process, and never stop an export that also
uses good media. All fixtures are generated by the test itself (no third-party media) and each is
below 2 MB.

**Tests:** `crates/arc-media/tests/malformed.rs` (corpus + per-fixture contract) and
`crates/arc-cli/tests/render_e2e.rs::mixed_media_export_survives_an_unreadable_asset`
(good and broken media in one export).

## 1. Corpus

The base is a 4 s, 160×90, 30 fps FFV1/MKV counter video (~0.5 MB) written by
`arc_media::fixtures::write_counter_video`. Every derived file is smaller than the base.

| Fixture | How it is made | Size | Import check | Decode boundary |
|---|---|---|---|---|
| `empty.mkv` | zero bytes | 0 B | `Offline` | `open` → `MediaError::Decode` |
| `text.mp4` | text bytes | 20 B | `Offline` | `open` → `MediaError::Decode` |
| `truncated.mkv` | first 25 % of the base (header claims 4 s, ~1 s present) | ~0.12 MB | **`Offline`** (test decode at 2 s produces no frames) | `open` may succeed; a frame past the data is `EndOfStream` |
| `half.mkv` | first 50 % of the base | ~0.25 MB | `Offline` | as above |
| `no_magic.mkv` | first 16 bytes zeroed (EBML magic gone) | ~0.5 MB | `Offline` | `open` → `MediaError::Decode` |
| `bad_header.mkv` | first 512 bytes overwritten with `0xFF` | ~0.5 MB | `Offline` | `open` → `MediaError::Decode` |
| `mid_corrupt.mkv` | 4 KiB of `0xA5` in the middle of the payload | ~0.5 MB | `Ok` (FFV1 conceals the damaged frames) | decodes; damaged frames are garbage, no crash |
| `bad_index.mp4` | valid MPEG-4/MP4 with 256 bytes of the `moov` box overwritten | ~0.1 MB | `Offline` | `open`/`frame_at` → typed error |
| `jpeg_as_video.mkv` | a JPEG renamed to `.mkv` | ~0.02 MB | `Ok` (`Image`, mjpeg) — ffprobe reads content, not the extension | decodes as a still |

`mid_corrupt.mkv` and `jpeg_as_video.mkv` are intentionally *not* refused: the first still decodes
(damaged frames are concealed) and the second is a valid image with a misleading name. They are in
the corpus to prove the no-crash contract, not the refusal path. Every other fixture must be
refused by the import check.

## 2. Error and availability contract

1. **Import check** (`arc_media::probe::import_check`) classifies every unreadable file as
   `Offline { reason }` (or `Quarantined { reason, .. }` when the child process crashed or timed
   out). The session layer refuses to import such a file, so it never becomes an asset.
2. **Truncation detection (video and audio, P3-1).** The test decode runs ffmpeg with
   `-progress pipe:1`. For a **video** asset a decode that produces **zero frames** at the start,
   middle or last second is `Offline` ("no video frames"). For **audio-only** media there are no
   frames to count, so the decoded `out_time_us` is compared with the window the probe promised
   (`min(1 s, remaining duration)`): less than half of it is `Offline` ("no audio output for the
   expected window"). A short but valid audio file is judged against its own duration, and images
   are not judged at all. Before this change a truncated container whose header still parsed was
   accepted, because ffmpeg exits 0 when a seek lands past the data.
3. **Decode boundary** (`VideoDecoder::open` / `frame_at`, `AudioDecoder::open` / `read`) returns
   `Result<_, MediaError>`; `MediaError::Decode(String)` carries the libav error text,
   `MediaError::EndOfStream` is an exhausted stream, `MediaError::Path` a refused path. No media
   call panics or aborts on the corpus.
4. **Implausible dimensions (new).** `VideoDecoder::open` rejects a frame buffer over 2^28 pixels
   (1 GiB RGBA) with a typed error before allocating, so a corrupt header cannot abort the process
   on the allocation. 65535×65535 and `u32::MAX`×2 are covered by a unit test.
5. **Availability marking.** The exporter keeps one decoder entry per asset; a failed `open` records
   the asset as unavailable and adds `video for <asset> unavailable: <error>` to the export report's
   `warnings`. The clip renders the background for its range; other clips are unaffected.
6. **Engine continues.** The project and session are untouched: `describe` still succeeds after the
   mixed export, and decode failures are per-asset, not per-process.

### Why no `catch_unwind`

`catch_unwind` is not used for the decode boundary: media failures already arrive as `Result` codes
from the C shim, and a native fault inside FFmpeg is not recoverable in-process — Rust cannot catch
it, and catching a panic would leave the decoder handle in an unknown state. The containment
boundary is the export child process (`arcline-cli render`, spawned by `job.submit`), which a crash
can take down without touching the editing session. In-process preview (Phase C) must therefore run
decoders on worker threads with the same per-asset error contract, not with `catch_unwind` around
the FFI.

## 3. Mixed-media export

`mixed_media_export_survives_an_unreadable_asset` builds a 30 fps, 320×180 project with two assets
imported while both were valid; the second file is overwritten with garbage after import (a real
"media changed on disk" case), then the project is saved with the broken clip on V2 after the good
clip on V1 and rendered. Assertions:

- the render exits 0 and writes all 60 frames;
- the report contains a warning naming the unavailable asset;
- frames 0–29 (the intact clip) are frame-exact by counter;
- the unavailable clip's frames (30–59) are pure black, not a stale frame;
- `describe` still works afterwards.

## 4. Known limits

- **No crashing/hanging fixture.** The `Quarantined` branch requires media that crashes or hangs
  `ffprobe`/`ffmpeg` inside the import check. Producing such a file deliberately means a
  decoder-crash PoC, which was not attempted; the branch is implemented and reviewed but not
  exercised by a test. This is the remaining half of the Phase B "mutated-media corpus" criterion.
- The corpus exercises container-level damage. Bit-level codec fuzzing (for example a fuzzed FFV1
  slice) is future work and belongs with the `cargo-fuzz` harness.
